# AI Runtime：能力可增强，权限和事实主人不变

本文件定义权限与执行协议的架构正文。领域归属见 [MODULES](MODULES.md)，文件/备份/Secret 见 [DATA](DATA.md)。依据为 AI-01～18 及相关 DM/UX；不增加通用自主 Agent 产品、全库记忆或自动正式写入。

<a id="position"></a>
## 1. Runtime 放在哪里

**AI Runtime 是后端中的受约束应用协调边界，不是正式事实 Domain，也不只是一个调用模型的 SDK。**

```text
业务模块：定义任务目的、合法材料、输出类型、领域校验和正式写入能力
                    ↓ 受限 TaskPolicy / ProposalTarget 接口
AI Runtime：授权 → Context → 预算 → 外发 → 输出校验 → 待处理内容 → 回执
                    ↓ 窄技术接口
Platform：LLM adapter / Search adapter / Feishu 只读 adapter / Secret bridge
```

Runtime 保存任务和 Proposal 状态；Resume/Wiki/Research 等仍拥有正式内容。Provider adapter 只负责真实网络协议，不读全库、不选择任务目标、不写业务事实。Context broker 只返回本次获准内容，不成为新的知识正本。

模型能力增强时，可以在同一许可内更准确地选资料、规划下一步、产生更好提案。允许替换的是 planner/task driver/model adapter；不替换的是身份来源、范围授权、外发检查、预算账本和领域写入 owner。首版只登记冻结规格已有任务，不引入任意 shell、SQL、JS、文件遍历或浏览器脚本工具。

<a id="actors"></a>
## 2. 行为身份不能靠模型自报

### 2.1 三种调用者，权限不串线

| 调用来源 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 可信交互会话中的真实用户 | 手工保存直接生效；确认任务范围；接受/编辑接受/拒绝；明确现实事件 | 仍需经过领域校验和并发检查 |
| 本次任务的 AI executor / 子任务 / AI UI adapter | 调用获准 discover/read/search/llm/propose 等能力 | 模拟 user 身份；点击自己的接受；调用任意手工写入 API |
| 外部材料、Provider 响应、导入数据 | 作为带来源性质的数据被读取 | 声明权限、扩展目标、注入调用者身份、替换用户确认 |

Actor 由后端接入的可信 transport/capability 创建，不能取自模型 JSON、提示词、DOM 字段或 `userApproved=true`。UI 路由名叫“手工编辑”不改变操作者身份；AI 通过应用内 UI 工具填入字段，仍沿 AI actor 通道，只能产生草稿/提案。（AI-01）

**没有向 AI 注册正式 UI 会话的 preload、审批端点或通用输入自动化能力。** AI-origin 草稿在应用内携带不可由模型抹掉的来源标记，进入手工编辑界面也不能自动保存；真实用户编辑后明确采用，仍按对应审批协议生效。普通用户自主手工修改不被迫走一次额外 AI 审批。

### 2.2 安全保证的边界

本设计防御应用支持的 AI/工具通道、恶意材料和未授权外部网页；不宣称能从鼠标坐标或 `event.isTrusted` 完美识别谁在操作。**不向 Runtime 开放操作系统级 computer-use、任意进程执行或用户会话凭据。** 能完全控制当前 macOS 用户会话的外部恶意进程不在这份应用权限边界能独立解决的范围内。

未来若产品新增 OS/UI 自动化，必须先提供独立可信的人工确认路径，绑定当前目标与具体修改内容，并禁止该自动化代为确认；否则不能接入正式写入口。不能一边给模型无约束操作用户桌面的权限，一边声称现有 Actor 字段已解决 AI-01。此限制保护未来增强路径，不要求现在制造通用人机身份平台。

<a id="grants"></a>
## 3. 单次授权与有限任务授权

### 3.1 公共授权维度

每份许可包含目标、作用对象、允许发现范围、允许读取范围、允许外发范围、真实接收方、预算/期限/停止条件，以及允许的产出类型。这些维度独立，不用一个 `scope=all` 或 `canAI=true` 合并。

| 维度 | 必须明确的内容 |
| --- | --- |
| 任务 | 本次目标、目标对象、允许输出类型；不是“随便帮助我”永久许可 |
| discover | 可以发现哪些对象及其哪些元数据；标题/命中片段也可能敏感 |
| read | 可读正文的对象/材料集合、版本或明确选择规则、字段/片段；不按关联递归 |
| egress | 可外发哪些材料，以及字段/摘录/摘要/全文/派生 query 等粒度 |
| recipient | LLM 与 Search 分别列出真实服务、endpoint、账号/凭据 generation、模型/产品标识 |
| budget | 根任务总上限、请求/输入输出等可执行限制、费用上限的计量依据；子任务共享 |
| validity | workspaceInstance、backendGeneration、有效期、撤销/停止条件、剩余权限；连接代次只校验通道，不重建任务权限 |
| output | 允许生成哪个域的哪些 Proposal/草稿；不授予正式事实写权限 |

范围内按需连续工作不反复要求用户批准同一范围；范围扩大、接收方改变或超预算才停下来重新确认。权限保守不是“每次工具调用都弹窗”。（AI-07、17）

### 3.2 单次模式：最终实际请求的确认

```text
准备本地材料（无外发）
 → 按真实 adapter 生成最终请求 payload/接收方/费用限制
 → 形成不可变 request manifest + digest
 → 用户看到真实内容与缺项，明确确认
 → 检查内容、依赖、Provider generation、预算、撤销状态
 → 原子消费一次许可并记账
 → 由唯一 dispatcher 发送这份请求
```

预览必须来自准备发送的真实材料，不是简化示例；Key 不进入预览，接收账号/服务身份必须可辨认。工具定义、系统提示、附件内容、查询词及会影响数据外发的请求项均在 manifest 的受控边界内。超大正文可分层展开，但不得以折叠隐藏“实际还发了其他材料”。

确认后不能再悄悄附加 Profile、读新文件、换模型/endpoint、改预算或重新拼接其他材料。影响内容/范围/接收方/预算的变化使许可失效；SDK 自动重试、自动 Provider fallback、自动额外修复调用关闭。准备预览不去查询外部定价、测试连接或调用模型。（AI-07、14）

### 3.3 有限模式：每一步仍有实际请求 manifest

有限授权批准一个明确任务的边界，不冻结所有未来步骤的正文。Runtime 每次 discover/read/send 前检查当前许可和剩余额度，并记录实际选择的材料/接收方；只要在范围内可继续。最终每次外发仍有可回看的实际 manifest，不能只有首次模糊授权的截图。

子任务引用同一根任务预算和权限树，只能取父权限与剩余额度的交集；不能新建不受父预算约束的根任务，不能通过“改名为总结/检查”扩大外发粒度。父任务停止或材料撤销立即影响未执行子步骤。（AI-07、17）

授权绑定当前 workspaceInstance 和 backendGeneration，子任务仍取父权限交集并共用根预算。**执行 capability 不随业务备份持久化**；普通 backend restart 保留资料身份但更换启动代次，旧能力无效；恢复/切库同时改变资料身份。仅 MessagePort 重连不自动生成新任务/许可，仍活着的已授权后台任务可查询与接续，不因 UI 重连而重放命令。

<a id="context"></a>
## 4. Context：渐进取得，不是全库装载

### 4.1 四步能力

`discover candidates → read selected current records → read authorized related Raw → propose changes`。

每一步由 Context broker 调用 actual owner 的只读接口，返回内容与 source/version/scope/provenance。发现三个相关 Project 不意味着读取其所有任职/聊天；读取项目也不意味着可外发其 Raw。Raw 可在获准后直接按需读取，无须先存在 Wiki。（AI-03～04）

Query cache、任务内摘要、已打开的材料和已下载到 staging 的文件都受当前许可约束。撤销后缓存命中不能绕过检查。读取过程中权限发生变化，在交给下一处理步骤前再次检查；不要因为网络/磁盘读取已开始就把结果自动继续送给模型。

本地全文索引可服务候选发现，但没有发现权限的对象不进入搜索输出；没有正文权限的 snippets 不返回。Context 读取能力不会暴露全局文件搜索、反馈、日志、开发聊天、备份、凭据库。（AI-16）

<a id="trusted-provenance"></a>
### 4.2 权限来源链由系统按真实输入计算

**可信 input manifest 由 Context/执行入口计算，模型 citation 只解释证据。**每次把实际内容交给模型、解析器、摘要处理器或子任务之前，Runtime/受信生产者入口记录实际提供的 source owner、对象、版本/片段、来源性质、权限限制、workspaceInstance 与清除代次。没有送给该处理器的库内材料不凭关联加入；真正送过的材料不能由模型漏引或改写后移除。

派生结果继承该处理步骤全部实际输入的权限来源链；摘要再被读取时沿可信链传递，包含对话历史、工具返回、隐式拼接上下文和复用缓存。混合输出无法可靠拆分时采用全部输入的限制。只有由系统实现并验证的隔离步骤，确实未收到其他输入，才允许更窄集合；模型声称“本段没用敏感 A”不构成隔离证据。

| 信息 | 谁计算 | 用途 |
| --- | --- | --- |
| authority provenance | Runtime/受信输入边界根据实际交付内容计算，不可由模型缩小 | 读取/外发约束传播、子任务、缓存与永久清除追踪 |
| evidence citation | 模型提出，系统校验确实存在且在相应证据集合内 | 解释结论依据；不能证明权限或删减实际输入集合 |
| semantic dependency set | 对应 TaskPolicy/target owner 依据具体变更和来源合同建立、验证 | Apply 的字段/区块、关键关系、实际证据版本检查；不能由模型任意省略关键依赖 |

这些是同一流程的不同职责，不建立新事实库。权限来源链保留所有实际输入，并不等于用“全库 revision”作为所有 Proposal 的冲突键。来源记录保留实际读取快照的版本；当前内容的关键字段/版本如何影响目标变更由 owner 的依赖规则裁决。真正用于支撑变更的来源及其关键更正必须命中冲突；证据已无法核对时明确 stale/不可用，不拿最新原文冒充旧证据。仅作为目标上下文的无关区块修改，不应因文稿总 revision 变化废掉其他建议。Input provenance 的历史快照标识本身不构成“永远保存旧全文”的保留要求。

本地可读、禁止外发的原文不能先交远端模型摘要。摘要、改写、提取词和派生 query 同样受原权限限制；允许“摘要”不自动允许混入未授权字段。首版没有必须提供本地模型的承诺，可使用用户明确摘录或本地确定性处理；无法满足范围则请求扩权或结束。（AI-07、08、16）

Profile 实际身份字段默认最小化；自由正文不能承诺万能 PII 脱敏，仍需检测提示和实际外发预览。Greeting 必要署名单列姓名授权，不顺带发送电话/邮箱。（AI-15）

以上 input manifest 同时用于 [DATA §7.2](DATA.md#persistence-fence) 的持久化闸门：被清除的实际输入 A 即使没有出现在 citation 中，派生摘要/Proposal/PDF 也不得以“只引用 B”为由重新保存。

### 4.3 证据性质不得在 Context 中漂白

至少保留来源类别、真实/模拟、用户记录/AI 推断、待处理/已采纳、确认/独立核验、引用版本和当前可读状态。来源存在不代表结论真实，用户采纳也不代表独立核实。

模拟回流只接受用户主动选择并确认真实含义的片段，输出仅限允许的 Personal/Cognition/Project Wiki Proposal。模拟面试官的虚构业务、薪资和要求不能进入真实公司研究；用户扮演一个角色说出的句子也不能自动算本人真实经历。（DM-30、AI-06、16）

<a id="task-types"></a>
## 5. 只支持冻结任务，按域登记策略

| 任务驱动 | 主要输入原则 | 合法产出/生效入口 |
| --- | --- | --- |
| Resume 优化 | 当前机会/JD/必要当前简历与研究，按需找获准项目/任职/Wiki/Raw；排除其他简历整库与默认身份实际值 | Resume 逐条 Proposal；不整份替换文稿、不改 Profile |
| Wiki 整理 | 明确目标范围、获准材料、当前对应知识；比较实际变化 | Wiki 逐条 Proposal；零修改正常完成 |
| Company/Opportunity 研究 | 使用公网搜索时 Search 与 LLM 分开；也可仅用获准的既有材料，包括真实 Transcript / Final Review | 按目标 owner 的受控 Research Proposal 组；无需先 Search，不写重复 Wiki 正文 |
| Greeting/沟通草稿 | 本次沟通背景；署名等字段独立授权 | 可编辑草稿，用户采用后写当前草稿，不标记已发送 |
| Interview Preparation | 对应真实轮次、实际投递状态/材料、获准研究/沟通等 | 一份可编辑准备草稿；无投递也可完成并明确缺项 |
| Final Review | 当前 session Transcript、真实/模拟性质、获准背景 | 一份可编辑复盘草稿；真实 Transcript/Review 还可经明确任务向 Research 产生受控 Proposal，不自动写入、不强迫 Search |
| Offer 分析/谈薪草稿 | 当前真实条件、原件及授权背景 | 分析/草稿；不能代替用户修改有效条件、接受 Offer 或建立任职 |
| 本地/飞书导入 | 候选发现、选择正文、预览、保存 Raw 分步；保存原预览内容 | 导入保存是明确独立操作；之后 AI 整理另走任务授权 |

真实面试到研究的路径对照 AI-02 / J-05：用户选择获准真实材料 → Runtime 记录可信输入 → 对应 Research owner 的 Proposal → 用户接受。模拟素材仍只按 §4.3 的范围回流，不能借 Review 入口写入真实 Research。

实际实现任务时直接对照 AI-02 的细项，不能把此摘要当成扩大默认 Context 的依据。任务策略按业务模块登记，Runtime 不在一个巨大 `task-switch.ts` 内重写每域规则。

### 5.1 Search 与 LLM 必须分开

Search adapter 接收明确获准查询；LLM adapter 接收另外准备的内容。查询含内部代号/薪资/姓名时，不因它叫搜索词就自动外发。搜索结果形成 SearchRun 的真实返回集合，Search-backed Proposal 只能引用其中有效来源。既有 Research/历史链接可作为授权证据，但标为既有资料，不虚构成本轮搜索。（AI-08）

本轮搜索若没有可信返回，输出零结果/失败，不补造 URL。模型给出的 URL 不自动成为已访问证据。需要继续访问页面时是受限网络动作，检查目标/预算/读取范围，拒绝本机/私网/文件协议及不获准重定向；远端网页里的指令不授予新工具。

### 5.2 Import 不等于 AI 外发

候选元数据查询、正文读取、预览保存、AI 整理各自分离。有限授权可覆盖明确的一组导入读取步骤，但不能把批准读取某文档理解为可上传其正文给 LLM。预览后源文档变化，保存的必须是已看过的内容，或明确刷新预览，不能静默换一版。相同保存命令只生成一份 Raw；取消不留空对象。解析/导入产生的候选和文件在每次持久化前都检查来源/目标清除代次；不允许晚到 import 恢复已清除内容。Raw 生命周期仍按 DM-12 的具体业务语义。（AI-09）

飞书 adapter 只提供冻结需求里的读取与导入能力，不暴露写入/上传接口。飞书登录身份与 Profile 不联动。首版优先窄的官方读取 API adapter，不引入任意 CLI 执行器；实际应用权限、服务范围和当前官方接口在实现该 adapter 时另做核对/验收，不能把本轮架构设计说成飞书已连接。

<a id="dispatch-budget"></a>
## 6. Provider、预算、停止与派发

### 6.1 一个真实外发入口

后端外部网络能力经 dispatcher 统一检查，再交指定 adapter。没有业务模块直接 new SDK 后绕过检查。adapter 声明操作种类、接收方、可预览序列化器、资源上限、重试/查询结果能力、响应校验器。模型默认重试/遥测/自动工具执行关闭，不通过 SDK 偷偷附加内容。

Provider 绑定包含服务类型、实际 endpoint、账号/credential generation 与所选模型；任何会改变接收方或用途的变化使旧确认失效。Secret 只在最终实际调用时由受信桥取得，处理见 DATA §9。连接测试是独立明确操作，不借保存 Key 或准备任务顺便发一次请求。（AI-14）

### 6.2 根任务共享预算

每次发送前在根任务账本预留本次资源/费用上限，所有子任务共用。预留、许可消费和 operation intent 以本地事务记录。并行子任务不能各自看到同一份剩余额度然后重复花费。

任务预算至少有可执行的请求次数、输出上限和相应输入/工具限制；货币上限只有在 adapter 能提供可信计费规则与本次最大费用界限时才作为硬保证。无法给出可执行上界时，必须明确费用估计的局限并使用用户认可的硬资源限制；若用户要求不可超的货币上限且不能保证，就阻止这次派发，不能以估算冒充保证。

外部结果未知时，相应预留不能当作“没有花钱”释放。确认未发送/未计费或拿到可核对结算后才调整。新请求 B 与 A 的可能重复费用单列；同一有限任务的 B 仍占该根任务剩余额度。用户另建独立任务需看到 A 尚不明确，不暗中重置预算。（AI-12、17）

### 6.3 撤销、慢数据库与迟到响应

真实 transport handoff 与许可撤销在**独立控制事件循环**中串行裁决。先通过唯一写 worker 记录预算预留/operation intent，返回后在紧邻 handoff 的临界区检查当前活闸门、Provider generation、原 request manifest 与有效预留；中间不能异步替换/追加输入。同步 SQL、索引和 backup 不运行在该循环，安排见 DATA §1.1。

stop/revoke 先到控制器：立即关闭对应根任务及子任务后续读/工具/外发入口，尚未 handoff 的请求不得发送，缓存也不能绕过。即使 intent 稍后成功，dispatcher 也须拒绝发送并记录可核对状态。停止记录由写 worker 随后持久化；控制阻止已生效与记录尚待确认分别呈现。程序崩溃后所有旧执行能力因 backendGeneration 改变而失效，不从数据库 running 状态恢复。

handoff 先发生：尽力取消等待/传输，不承诺远端未处理或未计费。崩在 intent 与 handoff 之间、无法证明是否发出时记 outcome_unknown；不释放未知费用、不自动 retry/fallback。用户 stop、有效期到期、预算用尽、资料撤销和 Provider 停用使用同一执行闸门。（AI-07、12、17）

**迟到结果仅在原任务仍有合法内容保留范围且通过持久化闸门时可保存。**不能触发后续调用或自动 Apply。来源或目标被清除、生产者/资料身份失效时，丢弃正文、patch、摘要和文件，只留不含敏感内容的状态原因；覆盖 AI、parser、import、PDF 等全部生产者。已发远端副本无法撤回与本地禁止再落盘是两个不同保证。

<a id="proposal-apply"></a>
## 7. Proposal / Apply：一个用户动作，一次原子提交

### 7.1 产出不是事实

Provider 返回必须先通过闭合 Schema、对象/字段/来源集合、任务输出类型与真实性标签校验。未通过就保存可解释失败状态，不能静默修成可应用提案；修复若需另一次模型调用，属于新的获准外发。合法零修改可以正常结束。（AI-18）

持久 Proposal 至少包含目标 owner、before/after 或明确变更、理由、证据、未知项、owner 验证的 semantic dependencies、不可由模型删减的 trusted input provenance、来源性质、任务关联和处理状态。保存之前通过 DATA §7.2 的清除/身份闸门；无效输出也不能写入一个绕过清除的 debug 正文库。草稿采用遵循同样的权限、冲突与原子提交规则。

<a id="atomic-apply"></a>
### 7.2 人工接受：所有最终检查和修改在同一正式事务

事务外仅准备不可变用户意图、候选 patch 和已经受保护的文件；事务外的预览、权限检查或读取结果均不能作为最终授权依据。`apply-proposal` 在唯一写执行 worker 中开启同一 `BEGIN IMMEDIATE`/UnitOfWork，执行下列步骤直至 COMMIT：[S41]

| 同一正式事务中的顺序 | 必须读取/检查/提交的内容 |
| --- | --- |
| 1. 身份与幂等 | 当前资料实例、可信 human actor/接入代次及当前本地写权限；原 commandId/operation/payload；已成功重复只返回可读取的原 receipt |
| 2. 当前 Proposal 与目标 | 当前 pending 状态、实际目标 owner/身份/写字段、用户本次确认的修改；不存在或被清除则拒绝 |
| 3. 实际来源 | 系统保存的 trusted provenance 与实际 source owner 的当前存在性、访问限制、清除代次；证据 citation 必须真实有效，不能取代输入集合。历史 Context 快照版本用于追溯，不强迫所有旧 Context 全文永久可读 |
| 4. 关键依赖 | before 值、区块/字段依赖、证据版本、关键关系及 owner 合法状态；禁止沿用事务外 R1 检查结果跳过当前 R2 |
| 5. Domain 修改 | 只调用 target owner 的公开正式写能力；同一 UnitOfWork，不允许私有跨表写或内部另行 commit |
| 6. Proposal 与文件保留 | 标记本次处理状态；若涉及文件，在同一事务验证 publish hold 并交接为正式 retention |
| 7. 回执与提交 | 写入本次 command receipt，与领域 revision/必要历史/Proposal 状态一起 COMMIT |

任一最终检查失败则本次全部不生效：不改正式资料、不留下 accepted 的半状态、不返回成功 receipt；给出可比较冲突及原 command 关联，未采用项仍 pending。事务中不等待网络、用户输入、文件生成或长时间复制；准备不足时退出准备流程，不能先提交一半。

**权限时序：**本地权限与来源变更也经同一写入口，以正式事务顺序决定先后，不能在其他 worker 直接改表。Runtime 的 stop/revoke 立即收紧外发能力，但不代表撤回用户新发起的本地接受权；Apply 不持旧 task grant 作为正式写许可。连接失效前已经线性化的本地短事务可完成，后来的命令必须失败；新连接不能自动续写。恢复的 pending Proposal 可由当前用户进行新的本地接受，仍须执行以上全部检查。

| 产出类型 | 接受粒度 |
| --- | --- |
| Wiki / Resume Proposal | 逐条原子接受；每条有自己的实际依赖 |
| Research Proposal | 用户选中的同一 Company 或 Opportunity owner 组在这一事务内全部校验/提交或全部不生效；明确冲突项 |
| Greeting / Preparation / Final Review | 一份可编辑草稿采用，原稿冲突先比较；同样不能事务外检查后盲写 |

接受立即生效，没有第二次 Apply。接受内容不等于独立核实、接受 Offer 或创建任职；这些现实动作仍走各自明确命令。忽略保持 pending、拒绝结束待办；跨 Company/Opportunity 研究不合成含糊的跨 owner 组。（AI-01、10～11）

### 7.3 依赖粒度：既不漏检，也不一改全废

每个提案由 TaskPolicy/target owner 记录并验证实际依赖的字段/区块值、关键关联和证据版本；模型不能省略必须的来源检查。权限 provenance 与清除检查覆盖所有实际输入，语义冲突检查按本条变更的关键依赖执行。例如 Resume 区块 A 的建议依赖该区块、对应证据和目标归属；接受与它无关的区块 B，不应仅因整份文稿 revision 增加就让 A 永久失效。

对用户普通保存可以用文档 revision 检测同时编辑；对 Proposal 生效必须在 §7.2 的同一正式写事务内按更细的 read/write dependency set 重新验证。若依赖真的变了，显示 stale/冲突，不隐式 rebase、更换来源或重新生成内容后沿用旧确认。两条提案写同一字段当然冲突；同组 Research 必须在同一事务检查所有选中项。（AI-11）

Resume 前端怎样把一次接受变成一个可撤销编辑事务，由 MODULES §7.3 统一定义。后端接受不可因 UI 撤销而回到 pending；撤销后的正文属于新的人工修改。

<a id="states"></a>
## 8. 状态模型：不要把所有“未知”挤进一个 status

| 记录层 | 代表什么 | 不能推断什么 |
| --- | --- | --- |
| Task | 任务目标、等待授权/执行中/已停止/已结束/需用户处理等协调状态 | 不能仅凭任务“结束”声称已产生正式事实 |
| ExternalOperation | 单次外发的未发送/已进入派发/处理中/已知成功/已知失败/outcome_unknown | 超时不等于未计费或远端失败 |
| Proposal / Draft | 持久待处理、接受、拒绝，另有当前依赖是否有效 | 模型完成不等于用户接受 |
| ContentAvailability | 正文已持久化、正文不可恢复、来源不可读等 | 有操作记录不等于有完整正文 |
| Local command receipt | 本次本地写入确已提交或仍待核对 | 回读失败不等于保存失败 |
| UI connection state | 当前窗口能否读取/订阅上述记录 | 断网/离页不等于任务取消或远端停止 |

Runtime 负责这些维度的合法组合，前端显示可理解的总结和原操作关联；不让各页面写自己的真假推断。没有独立存储一份与领域结果竞争的“AI 推进了机会”状态。

### 8.1 A unknown 后再发 B

A 达到无法确认结果的状态时，不自动重发。用户可选择继续等待、使用 Provider 可核对的结果查询能力，或明确发起 B；查询远端状态若本身需要外发也要在允许范围内，不能偷偷下载/再调用模型。

B 有新的 operation 身份和明确授权，显示 A 的潜在费用/迟到风险。A 后来返回，只能归 A；不能覆盖 B 的正文、冒充 B 成功或自动 Apply。A 仍须通过当前资料/启动身份及清除持久化闸门；失败时丢弃正文，不因“原任务”例外保存。用户可明确处理 A 已合法持久的结果，但必须重新校验当前权限/依赖。没有可靠结果查询能力的 Provider，A 可以永久 unknown，不强行“修复成失败”。（AI-12）

### 8.2 本地持久化结果未知

收到有效输出但保存结果未知时，先查同一 operation/command 的本地记录；已落盘恢复原内容，没有落盘不承诺重建。Provider 响应日志不能成为偷偷保留全文的第二个恢复库。不能用重新调用模型生成“差不多的结果”冒充恢复原结果。

<a id="recovery"></a>
## 9. Recovery、保留与清除

刷新或离开页面后，从后端重读已持久任务、Proposal/草稿及 receipt；不触发重新生成。当前运行实例还活着的任务按原许可继续，用户能重新进入进度；真正停止、权限过期、Provider 改变或实例重启后都不能无授权继续。

数据库保留任务历史与额度记账事实，执行 capability 明确绑定 workspaceInstance、backendGeneration 与 credential generation。普通后端重启保留资料身份以核对原 commandId，但废止旧执行权；恢复/切库新建资料身份。connectionGeneration 只属于通道，重连不产生新许可或自动重放命令。业务备份不保存执行 capability，旧 consumption/remaining 仅是当时历史；恢复后服务需重新配置/授权。（AI-13、MG-05）

恢复出的 pending Proposal 可以显示；用户当前明确接受它时，用当前权限、目标与依赖重新校验。这是新的人工本地写入，不是恢复旧 AI 写权限。退役任务类型的旧内容只能只读识别原状态，不重新挂到可执行任务驱动上。（MG-03）

任务中间摘要、原始请求 staging、未采用解析缓存有界保留，结束后清理或在明确故障保留策略到期时删除；pending 产出和用户需要回看的正式来源不是临时缓存，不按同一 TTL 自动丢弃。日志只保留操作种类、时间、范围摘要、接收方标识、资源账本、结果类别/错误码等必要信息，不写 Key 或整份私密 prompt。

DM-38 清除按可信实际输入 provenance 与目标查找正文、patch before/after、摘要、缓存和所有受管理副本。先立清除标记并关闭持久化准入，停止/隔离生产者和排空旧 sink，再清理已有内容；每个迟到结果落盘前复核。清除完成包含本地生产者已停止或写回已可靠阻止，不能只删除当前行。追溯只保留不含敏感正文的状态原因，细节以 DATA §7 为唯一协议正文。（AI-16、18）

<a id="evolution"></a>
## 10. 如何升级模型，而不重写权限模型

| 未来增强 | 应修改的位置 | 不得改变的位置 |
| --- | --- | --- |
| 更强多轮规划 | 具体 TaskDriver / planner | TaskPolicy、能力授予、外发粒度、根预算 |
| 更精准相关资料查找 | Context 检索策略/可重建索引 | actual owner、发现/读取授权、来源性质 |
| 新 LLM/Search 服务 | Platform adapter 与 Provider 配置 | 用户许可的真实接收方匹配、未知结果协议 |
| 更多并行子任务 | 有界 scheduler | 子权限交集与根任务原子预算 |
| 新文档解析器 | 只读有界 worker | 用户选择范围、材料 owner、不得直写业务 |
| 更好的建议效果 | Prompt/输出结构的兼容演进 | 用户接受、目标域校验、Apply 原子性 |

没有“模型够强后自动给全库权限”的升级开关。未来新能力的默认权限仍为空，只有登记后的任务策略和用户明确许可才能使用。

## 11. 对抗审查必须优先攻击的接缝

A. AI-origin 内容经 UI 手工保存路径洗成人工；B. read-only 材料变成摘要/query 后外发；C. 撤销与派发竞态；D. 子任务重复消费剩余预算；E. 旧备份复活授权/旧 Key；F. Proposal 组部分提交；G. 接受无关提案导致全部 stale；H. A unknown 被 B 覆盖；I. 无效输出“自动修复”偷偷增加一次调用；J. 调试缓存绕过敏感清除；K. 事务外检查 R1、事务内来源已为 R2；L. 模型漏引实际输入 A 以缩小权限；M. 清除后迟到 AI/parser/PDF 写回。

这些是需要执行的测试，不是已经观察到的实现问题；本轮没有业务代码或真实外发。
