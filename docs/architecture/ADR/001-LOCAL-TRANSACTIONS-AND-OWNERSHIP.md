# ADR-001｜单机事务边界与唯一业务 owner

**状态：V2 修订，等待最终架构审查。**  
**日期：2026-10-02**  
**依据：PR-01～04、DM-03、08～09、20、23、31、AI-10～11、MG-04。**

## 决定

一个本机资料实例使用一个业务 SQLite 数据库，由 backend utilityProcess 内的唯一写执行 worker 维护；控制循环不执行同步 SQL，受控长只读不取得业务写权。业务模块通过自己的正式写能力操作拥有的记录；跨域变化由同一应用内 workflow 在同一个 UnitOfWork 中协调。正式 Apply 的当前权限、目标、实际来源及关键依赖的最终检查，与 Domain 修改、Proposal 状态、retention handoff、receipt 同事务。Opportunity 子模块同样守公开/私有接口边界，共用事务不允许私有穿透。不拆成独立服务、独立业务数据库或事件总线，不以全局事件重放作为唯一状态正本。

具体 owner 和依赖只有 [MODULES](../MODULES.md#owners) 一份正文；事务、文件与恢复只有 [DATA](../DATA.md#sqlite) 一份正文。本 ADR 不建立第二套表设计或状态规则。

## 为什么值得记录

真正成本高的不是今后替换 SQLite 驱动，而是已经积累多年资料后再重新划分“哪一个对象拥有当时材料、当前条件、接受结果”。一开始把发送历史或 Proposal 接受拆到异步系统，会长期背负补偿、一致性和双正本问题。冻结需求没有必须跨机拆事务的压力。

## 接受的代价

模块可以独立开发，不能独立任意发布数据库协议；schema 升级与跨域事务要集成验证。唯一业务写入口要求短事务、受控维护和长只读隔离；stop/revoke 在独立控制循环先关闭执行闸门。以后真实需要多设备同步时，这个选择不能直接冒充已具备分布式一致性，需要新的产品决定和迁移计划。

## 放弃的替代

每域一个数据库/微服务会把本地可原子完成的 Proposal 接受、实际发送留存、Project 换任职变成跨服务协议。通用事件溯源会增加重放版本与隐私清除压力。两者当前没有足以抵偿成本的业务收益。

## 重新讨论的触发条件

经确认的新产品要求必须支持多设备同时写入、多人协作，或单机实测证明本机事务边界无法满足需求。不能仅因为 Agent 数量增加或框架流行而重开此决定。
