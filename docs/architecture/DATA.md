# 数据、历史、文件与恢复

本文件定义新系统的持久化边界，不推导或复制任何旧数据库。领域 owner 见 [MODULES](MODULES.md#owners)，AI 执行状态见 [AI-RUNTIME](AI-RUNTIME.md)。技术出处 `[Sxx]` 见 [官方来源](ARCHITECTURE.md#sources)。

<a id="sqlite"></a>
## 1. SQLite 是正确选择

Career 是一个本机用户的长期资料库，真实压力是关系约束、局部并发编辑、文件完整性和可靠恢复，不是跨机器高并发。**一个业务 SQLite 数据库 + 本地 blobs 目录**足够。不引入 PostgreSQL、Redis、消息中间件或独立向量服务。（PR-01、DM-03、MG-04）

使用 better-sqlite3 13.0.3 的 SQLite 3.53.4，Kysely 0.29.6 负责类型化 SQL。选择 query builder 而不是重量级 ORM：保留 SQL 事务、显式关系和迁移可读性，不把业务 owner 隐藏到自动级联/关系魔法里。Python 路线的 SQLAlchemy 和 Rust 路线同样能完成需求，但不是推荐运行栈。[S29–S32、S37]

后端 utilityProcess 保持唯一业务写进程；内部只有一个写执行 worker 持有 active SQLite 的可写连接。领域正式命令、Proposal Apply、retention、GC 认领和持久回执都通过这一入口。控制事件循环不执行同步 SQL。网络、解析、复制、PDF 均在正式业务事务外准备，最终检查和提交仍在事务内。

采用 WAL、明确 busy timeout、每连接启用外键校验；正式提交采用重视持久性的同步配置，具体 fsync/崩溃行为在 G1/G6 测试。读者不成为第二个写 owner；不放到网络共享盘或实时云同步目录里依赖多机锁。[S34]

数据库启动检查实际 `sqlite_version`、外键设置、FTS 编译能力和 schema 版本；不只看 npm 包名。SQLite 3.52.0 已撤回，不能因版本号更大或缓存文档而引入；选定引擎仍需和实际签名产物一起验证。[S29–S30]

<a id="database-execution"></a>
### 1.1 执行位置与控制路径

| 工作 | 执行位置 | 约束 |
| --- | --- | --- |
| stop、revoke、runtime control、最终网络 handoff | utilityProcess 控制事件循环 | 独立于同步 SQL；先关闭活闸门，再异步确认持久状态 |
| 正式领域写入、Apply、receipt、预算预留、hold/retention/GC claim | 唯一写执行 worker | 同一 active DB 可写连接；只接登记的内部能力，不能传入任意 SQL |
| 长只读、搜索、索引投影准备 | 有界只读 worker | readonly/query_only 连接；权限限定的查询计划、候选/字节预算、分页；输出交付前复核权限 |
| FTS 更新/merge、普通索引维护 | 写执行 worker 中的有界批次 | 不把一次全库 rebuild 塞进普通写命令；批次之间检查维护取消/暂停 |
| 不能切片的 DDL、清除整理、数据库压缩 | 明确维护模式，由唯一写执行器执行 | 暂停业务写入和新外发；控制循环仍接收 stop/revoke，界面如实显示维护中 |
| backup 的一致读取/复制/候选整理 | 受控备份 worker | 对 active DB 只读；只能写已登记的隔离候选，不成为第二 active writer |

worker 是本后端的实现细节，不是额外服务、Domain 或通用任务平台。跨线程只传受限命令/结果；UnitOfWork 与可写连接留在写 worker 内，同一事务中的 owner 能力也在那里执行，不跨线程共享 DB handle。[S38、S40]

控制器可立即阻止尚未 handoff 的外发，哪怕预算预留正在数据库队列中；预留返回后也必须重新过活闸门。持久 task 状态是记录，不能单凭一行 running 复活执行 capability。崩溃后新的 backendGeneration 使旧能力失效。Runtime stop 不等于撤回用户另行发起的本地 Apply；本地写权限与资料权限由正式写入口按事务顺序裁决，详见 AI-RUNTIME §7。

只读 worker 取消、CPU/返回大小上限及维护公平调度须在 G0/G6 用真实数据测量。不能把同线程 timer、返回行数 LIMIT 或“worker 已启动”作为控制及时性的证明；被阻塞的只读 worker 可终止并重建，不能中途强杀正式写事务来假装安全取消。

## 2. 本地布局与表归属

下面是未来运行资料布局示意，不是本轮在用户电脑上创建的目录。

```text
Application Support/Career/
  active-workspace-pointer       当前资料副本指针；不是 AI 授权
  managed-copies-manifest       受管理副本及状态；在任何复制前登记
  purge-control/                本机清除意图/副本处理进度；不含正文，不从备份回滚
  workspaces/<copy-id>/
    career.sqlite                唯一业务数据库
    blobs/                       已持久化、不可原地覆盖的文件字节
    staging/                     尚未发布的文件/渲染结果
    quarantine/                  额外文件或异常材料，不能伪装成有效正文
  backups/                       完整性可核对的恢复点
  security/                      受保护凭据密文/设备安全状态；不进业务备份
  cache/                         可重建缓存，不进业务备份
```

用户可以明确选择资料位置，但应用不自动把资料放进同步盘。目录与文件权限收紧到本机用户；这不等于业务数据库已经全文加密。**首版不默认增加 SQLCipher**；系统登录保护/磁盘加密能力属于设备保护，不得把 Keychain 保护 API Key 夸大成全库加密。若有应用级静态加密要求，需另评估密钥丢失与备份可恢复性，不静默改变数据格式。

### 2.1 表族，而不是一个全局 ORM schema

| 表族（逻辑名称，不是本轮 SQL） | 归属 |
| --- | --- |
| profile | 当前身份及 revision |
| opportunity/company、core、research、communication、submission、interview、offer | 对应 Opportunity 子模块；子模块不能随便互写 |
| project、participation、project-history | Project |
| employment、person、employment-history | Employment |
| wiki、wiki-revision、wiki-source-link | Wiki |
| resume、resume-version、export-snapshot、render-job | Resume |
| raw、raw-source-link、import-session | Materials |
| ai-task、external-operation、proposal、budget-ledger | AI Runtime；不存可恢复的执行凭证 |
| command-receipt、blob-metadata、publish-hold、retention-ref、GC claim、backup-manifest | Platform；保留理由由实际业务 owner 提供 |
| purge fence / producer persistence lease | 当前 source/target 的清除代次与持久化准入；不能成为第二事实库 |
| preferences、feedback | 各自辅助模块 |

使用模块前缀和本域 query 类型限制误写。需要共享一个 SQLite 事务，不意味着所有域都可以获得全库可写句柄。业务关系优先使用显式外键/唯一约束；跨类型 SourceRef 除类型检查外，必须通过实际 source owner 校验存在、版本与范围。不能宣称一个通用外键已覆盖多态来源的所有完整性问题。

强制唯一约束包括：每机会最多一个当前 Resume、一条首次 Submission、一个当前 Offer；每 Company/Opportunity 最多一个当前 Research；每 session 最多一个当前 Transcript/Final Review。这里的“零个”合法，不能为满足约束预建空对象。

<a id="time-history"></a>
## 3. 当前、历史、时间与未知值

### 3.1 不做通用事件溯源

当前对象行是当前状态正本；有业务意义的历史另外保存。一次合法变化在同一事务内更新当前值、必要历史和命令回执。不是重放一个全局事件流才能知道现在，也不是给每次敲字保存永久完整快照。

| 内容 | 保留策略 |
| --- | --- |
| 当前 Profile / 当前 Resume | 当前值 + 并发 revision；自动保存不等于命名版本 |
| Wiki | 同一身份下的有意义修订、退役/恢复历史 |
| Project/Employment/Person 角色、机会结果、轮次纠错 | 保存必要现实变化及纠错说明；真实变化与错误更正分开 |
| 可更正 Transcript/Communication 文本 | 保存当前正文与版本标识；不承诺永久保留全部旧全文 |
| 普通 ResumeVersion | 命名的内容快照 + 生成的 PDF；删除需检查独立留存引用 |
| ExportSnapshot | 未命名也保留可识别快照与 PDF，直到用户明确清除 |
| Submission / 后续发送 / Offer 接受依据 | 保存当时真实材料、条件与缺失语义；不随当前稿改变 |
| Proposal/AI 草稿 | 待处理内容按恢复需要持久化；已处理条目保留必要回执，不成为永远留存全文的秘密历史库 |
| 调试/临时摘要/解析缓存 | 有界、可清除，不进入职业事实或永久备份 |

来源被更正后，SourceRef 保留它当时引用的版本/定位。旧正文已不存在就显示不可读；不读取最新正文冒充旧证据。当前依赖条目提示待复核，不自动改写其陈述，也不把所有无关条目失效。（DM-12～15、AI-11、18）

确认/核验绑定陈述版本：改成另一句话后，旧确认不自动转移。用户采纳、用户确认、独立核验、推断/未知、当前有效性是不同字段/标记，不能压成一个 `verified`。（DM-10、AI-06）

### 3.2 时间不是一个万能时间戳

业务时间使用三种显式形态：**未知、仅日期、精确时刻（含原时区/偏移）**。另有系统记录时间 `recordedAt`。日期不转成午夜 UTC；未知不默认今天；只有用户明确“刚刚发生”才能记录当前时刻。（DM-40、UX-16）

同一现实事件的日期补录/纠错仍是同一身份。后来真实发生的变化是新历史项；保存表单的时间不是面试时间。未来计划离职日单独保存，不触发实际结束；实际开始前不创建已发生任职。（DM-17、34、39）

### 3.3 投递的“没有、未知、丢失、完整”

持久化使用显式判别结构，分别记录现实是否发生、是否用简历、当时内容是否已知、实际文件是否可得。不能用 `pdfId = null` 同时表示没用简历、文件丢失与保存失败。Greeting 同样区分未用、确实为空、未知、已知内容。（DM-23～25）

记录历史上已经丢失的原件是合法业务事实；**本次系统承诺保存文件却失败**是本次命令失败。后者不能降级成“历史缺失”来报告成功。

<a id="resume-data"></a>
## 4. Resume 数据格式、PDF 和实际发送

### 4.1 Career 自有文档格式

选择**版本化的 Career 结构化 JSON**为简历正文格式：稳定区块 ID、允许的段落/列表/强调/链接、经历/项目/教育/技能结构、有限布局属性。Tiptap 只是编辑适配器，不把整个第三方编辑器内部状态、任意 HTML/CSS、屏幕截图或 DOM 作为唯一正文。[S22]

适配器必须能往返保留支持的正文和格式；遇到未来未知结构，进入明确只读/兼容失败，不静默删除不认识的节点。schemaVersion 与 rendererVersion 不混淆；更新视觉不强制改正文。导入/粘贴去除脚本、事件属性和危险链接；不支持的格式给出可见降级。

当前简历只存受管理身份区的布局和字段位置，实际值来自 Profile。生成历史时，把当时 Profile 值与正文一起冻结。恢复旧版本到当前稿只恢复可编辑文稿及布局，当前身份仍读当前 Profile；不会把旧电话回写全局。（DM-01、21～22）

<a id="pdf-snapshot"></a>
### 4.2 PDF 快照绑定与发布协议

```text
用户发起命名版本/导出
 → composition 结束，当前保存取得已知 Resume revision
 → 命令明确携带 expected Resume revision + expected Profile revision
 → 同一短写事务：校验两者当前值/权限，冻结 RenderSnapshot 并记录原 RenderJob
 → 冻结 owner、正文和身份值、两种 revision、内容 hash、模板/字体/引擎版本
 → 无业务权限的打印 renderer 只加载该快照和本地受信资源
 → printToPDF 返回候选字节
 → 持久化前核对来源/目标清除代次；走 §5 hold/发布/retention 协议
 → 正式版本/导出物、业务 retention 与成功 receipt 同事务提交
```

若发起时的任一 revision 已变化，返回可比较冲突，不偷偷改用最新内容。命令明确选择已有不可变快照时绑定该快照 ID，不再次冻结当前稿。RenderJob 是待完成任务记录；它不是“已生成版本”的成功事实。重试只继续原 job 的冻结快照，不重新选当前材料。

打印 renderer 没有业务或 Secret capability，不加载远端字体、用户脚本、任意文件 URL；Desktop 输入是受限 Career 快照，不开放任意 HTML 打印。后端不 import React/页面实现，Desktop 装载独立 print build artifact。[S02、S04]

命名版本与未命名导出都必须在内容/PDF/引用完成后成功；renderer 崩溃、hash 校验失败或磁盘满不得生成假完成版本。PDF 要有真实文字层、可点击链接、明确 A4 溢出；中文字体和分页在真机检查，非零字节不等于验收通过。

编辑从 A 变成 B 后，A 的迟到 PDF 仍归原 Resume owner、Resume revision、Profile revision 和 snapshot/job；不能污染当前 B。若 A 的来源或目标已被永久清除，按 §7 丢弃迟到内容，不保存 PDF。历史 PDF 读取当时文件，不用新引擎重新生成来冒充；不承诺跨系统版本逐字节相同。

### 4.3 Submission 保存独立历史

选择导出物或普通版本用于登记实际发送时，由 `record-first-submission` workflow 从 Resume 读取冻结材料，再交 Opportunity 保存独立快照及 retention 引用。数据库唯一约束和 commandId 防止第二条首次投递。材料来自另一份简历也不转移其版本 owner，不自动给目标机会创建当前 Resume。

同一 PDF 字节可以物理去重，但 ResumeVersion 与 Submission 拥有各自独立的保留理由；删前者不能删后者。后续补发归 Communication 活动。未知内容不拿当前稿补齐；已知但原文件缺失则保留已知快照与缺失说明，不伪造 PDF。（DM-22～25、UX-08）

### 4.4 Offer 接受依据

Offer 保存当前有效条件的身份与有效性，真实正式替换产生新的条件依据身份。每次接受保留当时条件、未知项、原件或诚实的无原件/丢失说明；接受事件与当前结果由 Opportunity core 拥有，Offer 提供不可变条件依据，不另设竞争性的 accepted 状态；事件、依据引用和当前结果在同一事务中更新。

正式新条件替换已接受条件时，旧接受历史不删除，Opportunity 回到 active/Offer 等待新决定；普通谈薪消息或排版更正不能自动当成正式替换。招聘方撤回与用户误点接受的纠错使用不同命令，不改写过去真实接受过的事实。（DM-31、35）

<a id="file-commit"></a>
## 5. 文件发布、保留交接与 GC 互斥

SQLite 与文件系统不共用一个 rollback。采用下列最小本地协议，让已承诺的业务引用不会落到被回收的文件上；不建设通用两阶段提交平台。

```text
staging
 → publish hold（先持久化保留，GC 此后不能认领）
 → immutable blob（校验、持久化、原子发布）
 → 正式业务事务（全部最终校验）
 → retention handoff（仍在该事务内）
 → command receipt（仍在该事务内）
 → COMMIT 后才报告业务成功
```

### 5.1 发布的确定顺序

1. 登记原 command/job 的生产者身份、workspaceInstance、backendGeneration、可信来源/目标与清除代次；所有 staging 写入都经受控持久化入口。用户文件选择能力有范围、类型/尺寸限制；内部命名，不执行附件、不跟随任意 symlink。
2. 完整写入 staging 并核对尺寸/hash。**在 blob 进入 GC 可见目录之前**，经唯一写入口提交 `publish hold`，绑定原命令、来源链、blob incarnation 及恢复状态。创建 hold 必须拒绝已经 `delete_claimed` 的 incarnation。
3. 文件 broker 检查持久化准入，执行所需 fsync/目录持久化并原子发布不可变字节。发布失败不进入业务成功。blob 状态可恢复核对，只有校验完成的发布证明才允许引用。
4. 在同一个正式写事务中，重新校验当前 actor、目标/来源/关键依赖、清除代次、blob 发布状态和本命令 hold；由 owner 完成业务变化，建立正式 retention，交接/释放对应 publish hold，写入成功 receipt 后一起提交。事务内不等待 PDF、网络或大文件复制。
5. 成功由已提交 receipt 证明。hold 不能在正式 retention 建立前提前释放；响应丢失只能查原命令，不能重新选一份“当前”材料。

文件 hash 只证明字节/允许物理去重，不决定 Raw、事件或人物身份。物理去重只能复用仍可保留的、未被删除认领的 incarnation；路径/ID 不复用已经进入删除流程的 incarnation，避免旧 GC 异步删除误删新发布文件。

### 5.2 GC 的删除认领

GC 扫描只产生候选。真正删除前必须由**同一个写执行器**在短事务中检查没有 publish hold、业务 retention、备份 pin、有效生产者保留或维护阻断，并以条件更新认领 `delete_claimed`。hold 建立/转移、retention 增删和 GC claim 共用这一排序点，互斥检查不可放在事务外。

已 claim 的文件禁止新引用/新 hold；文件 broker 仅删除所认领的 incarnation，再记录完成。崩溃恢复继续同一 claim，不按过期扫描列表无条件 unlink。需要同内容时等待该删除完成后发布新 incarnation，或复用另一条合法已保留记录；不允许 claim 后“抢救”同路径造成 ABA 竞态。

发现 publish 残留时，先按原 command/job 和发布记录核对。只有原生产者已可靠终止/被隔离、原命令未成功、没有正式引用及其他保留理由，才能释放 hold 后交给 GC。**TTL 超时不能单独证明可删除**。备份、purge、GC 的维护顺序共用 DATA §7～8 的协调入口，不各自判断同一文件可删。

### 5.3 故障必须落到确定语义

| 切点 | 结果与允许恢复 |
| --- | --- |
| staging 写一半、hash 错误、必需文件磁盘满 | 没有业务成功；残留登记、隔离或清理 |
| hold 已提交，blob 未完整发布 | 保留原命令状态；同输入核对或终止，不生成正式材料 |
| blob 已发布，正式 DB 未提交 | 没有业务成功；hold 阻止 GC，按原命令继续核对/终止 |
| DB 已提交，UI 未收到 | 业务已成功；查询原 receipt，不重复创建事件 |
| PDF renderer 崩溃 | 没有成功版本；仅允许原冻结快照的本地重渲染 |
| 相同命令再次到达 | 返回原结果/原在途状态；相同 ID 不同 payload 拒绝 |
| GC、purge、backup 并发 | hold/retention/claim 与维护屏障决定顺序，不删除已承诺材料 |

本次保存失败不得改写成“历史原件丢失”。文件读取先通过 owner/retention/source 的当前权限，不开放按 hash 任意读的 API。用户导出到外部路径的成功与库内保留导出物的成功分别显示；覆盖行为明确。

### 5.4 回执、身份与清除

同一资料实例中 `commandId + operation` 唯一，绑定不可变 payload digest；正式业务结果与 receipt 同事务。普通 backend restart 不改变 workspaceInstance，因此仍能查询原回执；backend/connectionGeneration 不进入持久幂等身份。恢复/切库后旧回执仅作为原实例历史，不自动执行到新实例。

返回旧 receipt 也要检查当前权限与清除状态；可以返回“当时已提交、内容现已清除”的最小说明，不回放已清除正文。原始 payload/diff 不因幂等而永久保存；摘要化回执保留必要去重标识。未知/在途命令不按普通过期策略随意删除。

<a id="search"></a>
## 6. FTS5 与中文短查询的真实工作量

保留 SQLite FTS5 trigram 作为可重建派生索引。少于三个 Unicode 字符的 MATCH 不会匹配；某些没有足够连续字符的 LIKE/GLOB 会退化扫描。因此不能用 `LIKE ... LIMIT N` 加控制循环 timer 冒充扫描有界。[S35]

**一/二字 fallback 采用受控扫描：**先按获准 owner/scope 和可用关系索引选候选 ID；只读 worker 用主键游标分批读取限定记录/文本块。每批限制实际候选行数、读入字节、文本块大小与累计比较工作；正文在有界块中处理，跨块保留必要重叠。不能让一条无限长正文或一次全表 LIKE 消耗全部时间。达到候选/字节/比较预算即停止，返回 `partial / 结果未完整检索` 和可继续/收窄范围提示；只有已完成批准范围扫描才能返回完整的无结果。

查询计划须验证范围过滤和游标走索引；单批同步查询只准处理预先限量的候选，不使用 OFFSET 越翻越远。取消消息由独立控制器接收，有界 worker 批次间检查；超时可终止只读 worker。具体阈值在 G6 用中文一字、二字、无匹配、大正文、100+ 对象及更大合成资料实测，记录实际访问行/字节与控制响应，不在架构中虚构毫秒指标。FTS 长查询同样受 worker、输出和查询资源约束。

索引不是正文 owner；每域提供最小可搜索投影和来源定位。增量更新可恢复，坏/缺索引显示降级或不可用，清除删除 FTS 残留并在必要时重建。索引维护位置见 §1.1，不在控制循环全库 optimize。[S35、S38]

人工全库搜索与 AI candidate discovery 分别检查范围；没有正文读取权时不能通过 snippets、摘要、命中计数泄露内容。搜索返回前以及 Context 交给模型前复核当前权限/清除代次。语义向量若未来确有收益只能是受相同权限与清除约束的派生索引；本轮不增加独立向量库或默认外发 embedding。

<a id="purge"></a>
## 7. 永久清除、迟到结果与受管理副本

归档改变组织/可见性；纠正归属改变业务关系；永久清除才处理选定正文及其派生残留。三者不混用。共享材料/独立历史的 retention 由各 owner 判断，影响计划不能用无差别 cascade 代替用户选择。（DM-38）

<a id="managed-copies"></a>
### 7.1 一份受管理副本清单

应用在创建/复制任何可能含用户资料的目录**之前**，把 copy ID、来源谱系、路径、类型、状态与必要清除进度写入本机 `managed-copies-manifest`。它是本地维护清单，不是第二份业务事实库、任务权限库或新服务；不含正文和 Key，不随旧备份回滚。生产者使用的 source/target 清除代次由 active DB 的唯一写入口拥有；本机清除日志只记批准的副本范围与处理进度，不能授予读取、恢复或执行权。启动核对清单和受管理目录；未知残留隔离并纳入影响核对，不能忽略。

| 必须进入影响清单的地方 | 清除、备份与恢复要求 |
| --- | --- |
| current workspace | 正文、来源版本、历史、实际发送/接受依据、引用和必要清除墓碑 |
| managed old workspaces | 恢复/切库后保留的旧资料，回退可用不等于可免于清除 |
| restore candidates / quarantine | 验证前候选、异常/孤儿文件、失败恢复；均可能含真实内容 |
| 完整与 failed backups | 完整点的独立文件集合；失败点不得躲在成功点列表之外 |
| staging / 生产者临时结果 | AI、解析、导入、PDF、文件复制尚未发布内容 |
| caches / FTS / Proposal / summaries / blobs | 实际输入派生内容、before/after、请求暂存、自由页/WAL 及受管理临时文件 |

用户明确保留某个回退/备份副本时，显示“当前选定范围已清除，所列副本仍保留”；不能宣布所有受管理副本已清除。离线、不可访问或处理失败的副本列为未完成。受管理副本的创建和清除共用维护准入：清除计划冻结后不能偷偷产生未登记新副本；并发复制要么先完成并纳入计划，要么取消并清理候选。

**不承诺删除**系统级快照、SSD 法证残留、用户自行复制的文件、已经发送到外部服务的副本。受管理范围内仍须处理可访问的旧文件/WAL/FTS/缓存，不能用这些外部限制替代本地清理责任。

<a id="persistence-fence"></a>
### 7.2 所有生产者的持久化闸门

每个 AI/parser/import/PDF/backup 等生产者在首次读取前绑定 workspaceInstance、backendGeneration、producer ID、目标及可信实际输入来源。来源/目标具有**按对象或必要内容范围的清除代次**，不使用让全库 Proposal 失效的全局内容 revision。相同业务 ID 不用于复活已经永久清除的身份。

原件、摘要、patch、Proposal、缓存、staging、blob 与正式记录，每次准备持久化都经过同一准入机制：当前资料/启动身份有效、生产者未被撤销写回、所有实际输入及目标没有跨越清除标记。来源链按 AI-RUNTIME §4.2 计算，不能只看模型 citation 或目标是否存在。校验与取得有界写入 lease 在同一持久化闸门内；数据库正式写入/hold 建立/retention handoff 时还要在写事务内复核。

生产者不持有 active DB 写句柄、任意文件路径或清除后仍可自由写入的 FD。候选结果只能经受控 sink 分块写入。清除撤销旧 sink 准入，并等待已发放写入 lease 完成/关闭，或终止生产者并确认文件句柄关闭后，才删除残留。**检查一个布尔值后继续无限写文件不构成可靠隔离。**失效响应丢弃正文/patch/摘要/文件，只可记录不含敏感片段的状态原因。

### 7.3 清除的完成协议

1. 按实际 owner、来源谱系与受管理副本生成影响计划；说明历史材料、共享保留理由、任务及备份影响，取得用户明确范围选择。
2. 先持久化不含正文的本机清除意图和批准副本清单，再在唯一写入口复核计划依赖并提交 source/target 清除标记及清除进度；控制器关闭受影响任务的后续读/外发/持久化准入。意图、数据库标记或完成进度不一致时，重启先核对原清除任务并保持相关生产者写回关闭，不能误报完成；不一致不生成第二次清除范围。正在备份等维护冲突必须完成或取消后再推进，不能同时开放复制和销毁。
3. 停止或可靠隔离受影响的本地生产者；等待旧写 lease/打开的 sink 排空。已发远端请求无法撤回，但迟到响应不得持久化。已在标记之前提交的结果也必须纳入本次清理。
4. 在批准范围内处理正文、Proposal before/after、摘要、缓存、索引、文件与每一受管理副本；多批清理可恢复，期间对象保持不可读/不可写，不能局部开放为“完成”。blob 删除仍尊重独立 retention，明确批准的删除先撤销相应理由再认领。
5. 在维护窗口处理自由页/WAL/FTS 和临时副本，检查旧数据不会从受管理恢复点自动返回；清除标记与进度独立于旧业务备份回滚。失败明确标为未完整完成。
6. 只有所选范围的副本处理完毕、本机维护日志可持久核对，且本地生产者已停止或迟到写回被可靠阻止并排空，才记录完成 receipt；崩在最后状态确认之间只进入待核对，不重新开放生产者。清除后的旧任务回执只能返回无正文说明。

正常 stop 后的迟到 A 可归原任务，仅限 §7.2 仍准许保留；永久清除优先，禁止“按原任务保存”把已删除的资料改写回来。此协议覆盖所有本地结果生产者，不仅覆盖 AI。（AI-16、18）

<a id="backup"></a>
## 8. 自动备份、普通恢复与正式迁移

### 8.1 自动与手动共用一套正确流程

自动备份可启停、配置周期和保留数量；不新增后台系统 daemon。首次设置展示默认候选配置“应用运行时每日检查、保留 14 个完整恢复点”，用户启用后生效；这是可调整实现默认，不是新产品合同。未启用或应用退出期间没有备份应如实显示，启动/唤醒只补一个需要的恢复点，不伪造每个错过日期的副本。（UX-12、MG-04）

同一实例的手动/自动备份单飞；磁盘不足、备份目录不可用或资料不完整必须失败/标不完整，不能继续删除最后一个完整恢复点。新恢复点完整发布后才按保留策略清理旧完整点；隔离/失败点单列，不冲抵用户承诺的完整点数量。

### 8.2 一致且可清除的备份

```text
登记 managed copy 候选并取得备份/GC/purge/restore 维护屏障
 → 受控 worker 用只读源连接通过 SQLite Backup API 取得一致副本
 → 由副本数据库枚举应保留 blobs，建立保留 pin 后复制并核对
 → 在隔离候选中过滤不可备份内容、清空外部激活绑定
 → 生成全新的发布数据库文件，排除旧自由页/WAL/FTS/临时内容残留
 → 核对 schema、关系、来源、快照、blob hash/尺寸及实际缺失
 → manifest + 原子发布完整恢复点；释放 pin/维护屏障
```

活库业务可在一致快照取得后按正常规则继续写；GC/purge 与此备份不能争用快照所需字节。备份 worker 对 active DB 只读，对自己的候选可写；这不开放第二业务写入口。stop/revoke 始终由独立控制循环接收。用户要求清除而备份在进行时，可以取消并清理备份候选，不能把“排队”当“清除完成”。

不得直接复制活 `.sqlite` 忽略 WAL。SQLite Backup API 只保证数据库快照，外部 blob 集合仍由本协议对齐。[S34] 过滤后的发布副本采用新文件重建/受验证的紧凑重写，FTS/派生缓存不直接搬运，恢复后重建；**仅 DELETE 逻辑记录不能证明发布副本没有被排除内容残留**。含原内容的工作候选、WAL、failed backup 都保留清单状态直至处理完毕。G6 使用可识别测试敏感内容检查发布 DB/文件集合和临时残留；不声称 SSD 法证擦除。[S35]

备份保留业务数据、必要历史、持久 pending Proposal/任务回执、反馈与 retention 关系；排除真实 Key、vault 密文、可执行能力、设备安全状态、临时请求/解析/调试缓存。非敏感 Provider 标签只作历史提示，激活绑定清空。清除墓碑可保留最小状态，不携带已清除正文。（AI-13～14、MG-05）

完整性分别报告 DB/外键、跨类型引用、缺失文件、额外文件、hash 错误、快照关系和历史原本已知缺失。原件在备份前已诚实标为丢失，与本次复制失败分开。新完整点发布后才执行旧完整点保留数量策略；失败点不占完整点数量，仍在清除清单内。

<a id="restore"></a>
### 8.3 恢复：只选择一个验证通过的 active workspace

恢复包不可信。限制解压路径/总量，拒绝 symlink、路径穿越、任意绝对路径和备份夹带代码；只运行随受信应用发布的迁移。候选创建前登记 managed copy，验证数据库、blobs、manifest、来源/快照以及本机未完成清除意图和副本范围。恢复不能回滚本机维护进度或静默结束未完成清除。曾明确保留、因而未纳入完全清除的副本，在用户此次恢复的影响确认中如实列出将恢复的内容；按该次明确恢复决定处理，不擅自删除用户保留资料。已纳入清除范围而尚有残留的候选必须先处理或报告未完成，不能静默重新暴露。

切换前关闭新业务写入，停止/隔离旧生产者并排空文件 sink，关闭旧 DB 写连接；旧目录登记为 managed old workspace。验证候选后分配新的 workspaceInstance，持久化已验证的激活记录，然后以原子替换和必要目录持久化更新唯一 `active-workspace-pointer`。Main 只为指针选中的副本授予写锁，旧/新库不能同时 ready 为可写。

| 断电位置 | 启动选择 |
| --- | --- |
| 指针替换前 | 仍选旧已提交指针；候选为未激活受管理副本 |
| 原子替换后 | 只选新指针指向且校验通过的副本；旧库保持非 active |
| 指针损坏、目标缺失或校验失败 | 进入恢复只读/选择模式，关闭业务写入与外发；用户明确选择一个验证通过的副本后再提交新指针 |

不按目录 mtime、最大版本号或“最近一个库”自动猜 active；不因回退方便同时开放两个写者。active pointer 是本机运行元数据，导入包不能直接覆盖它。恢复/切换后旧目录仍纳入清除与备份影响清单；回退是另一次明确激活，取得新资料身份。

普通 backend restart 保留资料身份，只改变 backendGeneration；恢复/切库改变资料身份并关闭旧启动/连接能力。恢复后的服务保持未激活，需重新配置或明确重绑以及新任务授权；旧预算记录不代表剩余执行权，unknown 保留未知，备份点后未保存的费用/任务证据不能补造。（AI-12～14、MG-05）

pending Proposal 是可恢复内容，用户可凭当前权限按 AI-RUNTIME §7 进行新的本地接受。成功界面说明启用副本、资料/缺失/额外项、外部服务状态及回退副本保留情况；不完整材料不能只给绿色成功。

### 8.4 新系统 schema 升级与旧系统迁移是两件事

新应用自己的 schema 升级：每次先有可用恢复点、检查版本兼容、单实例维护锁；支持事务性 DDL 的步骤以事务提交，不能原子回滚的大文件转换先在新位置准备。旧应用不得打开新 schema 猜测运行。二进制回退必须配对应数据恢复点，不能只降级应用。（MG-04、UX-13）

正式旧 Career 迁移：**本轮不读旧系统、不设计旧字段映射、不运行迁移。** 未来单独授权后由独立导入适配器把盘点出的产品语义导入新系统 staging；真实/测试/未知分开，未知不猜。多条历史首次投递等冲突隔离给用户确认；退役记录只作为带原状态的历史资料，不重新获得执行入口。无来源、未知日期、模拟性质、AI 采纳与材料缺失不得洗成确定事实。J-09 普通恢复通过，不能作为正式迁移通过。（MG-01～03、06～07）

<a id="secrets"></a>
## 9. Secret：新 Key 只写输入，已存 Key 禁止回读

保留 Electron safeStorage，密文由应用保存、系统 Keychain 保护加解密能力；不把它称为全库加密。采用选定 Electron 44.5.1 已提供的异步 safeStorage 接口，避免系统授权交互阻塞 Main 的控制路径；稳定签名身份与更新后的 Keychain 行为必须通过真实签名包测试。[S36]

| 阶段 | 允许路径 | 禁止路径 |
| --- | --- | --- |
| 用户输入新 Key/替换 Key | 专用密码输入控件 → preload 的固定只写 Secret 操作 → Main secret adapter | 普通配置 DTO、通用 command payload/digest、Query cache、共享表单 store、自动保存/日志/遥测 |
| 安全保存 | Main 校验输入范围，异步加密、原子保存密文，成功后切绑定 | 安全存储失败时回退明文；保存时顺便测试连接/调用模型 |
| 使用已保存 Key | 受信 Provider adapter 经私有能力通道申请本次指定 credential generation，短期使用 | 返回任意 renderer、打印窗口、普通业务 Contract、SQL、环境变量/命令行、备份 |
| 读取配置状态 | 返回是否配置、接收方标签、非敏感标识和错误 | 回显明文、可还原片段、解密接口；用已有 Key 填回输入框 |

**边界如实声明：**普通 React 密码输入框在用户输入期间会短暂接触新 Key 明文；本设计不声称任何 renderer 永远见不到新值。该控件使用局部一次性 DOM/ref，不接入通用表单缓存。Secret 通道不复用通用命令 recorder；安全审计仅记录操作种类、结果与不含凭据的引用。提交、取消、失败、卸载时清空输入并释放缓冲引用，Main/adapter 尽早释放或清零可控 buffer；不承诺 JS 字符串内存的法证级擦除。

只写输入端校验 sender/frame、输入上限和请求关联；响应只有成功状态和 opaque credential ref，不包含 Key。保存失败要求用户重新输入，不能为了无感重试把原值放进持久 retry 队列。已保存 Key 没有任何 UI 回读能力；正常使用不经过新 Key 输入通道。

新值安全保存后才切 active binding。用户已停用/撤销的旧 credential generation 不得因新值失败复活。配置保存、解密可用、连接测试、单任务成功和输出可采纳分别记录；连接测试是用户明确发起的独立操作。（AI-14）

设备侧最小撤销状态不随业务备份恢复；执行能力绑定 workspaceInstance、backendGeneration 和当前 credential generation。安全存储不可用只禁用对应外部能力，不阻断人工业务；不增加新的常驻安全服务。

## 10. 数据层必须提供的可观察失败结果

最低需要区分：schema 不兼容、磁盘不足、文件缺失、hash 不符、历史原件原本不可得、数据库忙/只读、并发冲突、命令提交结果待核对、备份不完整、恢复副本不可用、安全存储不可用。错误应带处理建议和 owner，不泄露敏感正文/本机绝对路径。

这些是设计要求；数据库崩溃注入、原生驱动、文件发布、PDF、备份/恢复与清除测试均尚未执行。验收门统一见 DELIVERY，不把本文件视作 PASS 记录。
