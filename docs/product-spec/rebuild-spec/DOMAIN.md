# 领域语义草案｜R2

这里只定义“东西是什么、属于谁、什么会变化”，不定义数据库表、接口或框架。

## 关系速查

| 关系 | 正本条款 |
| --- | --- |
| 公司 → 多个机会；公司/机会各自当前研究 | DM-02、DM-08 |
| 机会 → 至多一份当前简历、一次正式投递、一个当前 Offer；多次沟通与多轮面试 | DM-03 |
| 当前简历 → 多个普通版本；导出物与实际发送材料有独立历史归属 | DM-21—DM-25 |
| 真实轮次 → 多次同机会模拟；轮次附属准备、文字稿、复盘 | DM-26—DM-30 |
| 项目 → 可选关联一段当前任职；任职 → 多个人物 | DM-16—DM-20 |
| 项目 ↔ 人物，多对多，每对有独立项目职责和历史语境 | DM-19、DM-20 |
| 原始材料 ↔ 知识，多对多来源引用；每条知识有明确范围 | DM-11—DM-15 |
| 当前基础资料 → 所有当前简历身份区；冻结历史不追改 | DM-01 |

“属于谁”表示业务所有权；“关联”不等于拥有、复制或有读取权限。数量为零可以是正常未创建，不等于错误。晚录、错录和后来真实变化的共同语义见 DM-39；业务时间见 DM-40。

<a id="DM-01"></a>
### DM-01｜基础资料：当前身份的唯一正本

**状态：目标**

姓名、联系方式和个人网页由基础资料统一维护。保存后同步所有当前简历的受管理身份区，新建当前稿使用最新资料；不改经历、技能、格式及其他表达。普通版本、导出历史、实际投递记录和已有 PDF 不追改。同步遇到并发编辑不能静默覆盖用户未保存内容。

用户在可编辑的当前简历纸面身份区直接修改受管理字段时，这个动作表示修改基础资料本身：保存后同步其他当前简历。若用户只想保留某个历史值，应通过历史版本/投递材料回看，而不是制造第二份当前身份正本。外部账号昵称、头像不自动成为简历真人身份。

<a id="DM-02"></a>
### DM-02｜公司与一次机会

**状态：目标**

一家公司可关联多个机会，并共享公司层面的研究。公司身份有歧义时让用户明确选择，不凭同名猜测合并。公司改名可以更新同一 Company 的当前名称；误选了另一家公司属于关系纠错，不能偷偷改写冻结历史材料里的当时文字。

Opportunity 表示一次具体求职尝试。**创建最低信息是公司＋岗位名称；JD 和招聘链接都可后补。** 缺 JD 只阻止真正依赖 JD 的分析，不阻止记录已发生的现实联系。同岗位真正重新尝试应创建新机会，不覆盖旧尝试。

本稿没有确认 Company 必须统一拥有 Employment；任职中的公司信息不自动建立额外身份关系。

<a id="DM-03"></a>
### DM-03｜机会内部归属与数量

**状态：目标**

一个机会有零或一份当前简历、零或一次首次正式投递记录、零或一个当前 Offer；可以有多次沟通、多轮面试和首次投递后的后续材料发送。每份当前简历有自己的普通版本。每个来源、提案和材料均须能识别所属对象。

准备简历、已有 JD、已有投递都不是记录真实沟通、面试或 Offer 的资格要求。

<a id="DM-04"></a>
### DM-04｜机会阶段、当前结果及真实变化

**状态：目标**

阶段为投递准备（界面可称“写简历”）、已投递、面试、Offer。当前结果独立为进行中、接受 Offer、招聘方终止、用户退出。“已结束”只是当前结果非进行中的视图，保留最后实际达到的阶段。

现实投递可推进到已投递；确认真实面试可推进到面试；现实收到 Offer 可直接推进到 Offer，即使没有登记前序投递或面试。改稿、生成 PDF、AI 成功、普通沟通记录或复盘都不自动推进阶段。

当前结果不是不可更改的历史抹除器。误操作按 DM-35 纠正；后来真实发生的新变化按 DM-39 记录并更新当前结果，同时保留过去确实发生过的接受、退出或终止历史。例如已接受后招聘方撤回，可以把当前结果更新为招聘方终止，但“用户曾在当时条件下接受”仍是历史事实。

<a id="DM-05"></a>
### DM-05｜非顺序现实事件可以直接记录

**状态：目标**

Career 按现实记录，不要求用户为了系统顺序制造假前置。没有正式投递记录时，可以新增真实招聘沟通、确认真实面试或记录现实收到的 Offer；这些动作各自只产生对应真实对象和必要阶段变化。

普通沟通本身不推进阶段；确认真实轮次进入面试；收到 Offer 进入 Offer。不能因为允许跳步，就自动补造 Submission、猜日期、建立不存在的面试，或允许第二次“首次正式投递”。晚录历史和后续真实变化遵守 DM-39。

<a id="DM-06"></a>
### DM-06｜结束机会后仍能如实记录历史和后续

**状态：目标**

结束不删除简历、投递材料、沟通、准备、文字稿、复盘与 Offer。历史可回看，允许更正其自身规则允许更正的现有内容。

结束后允许两类新增记录：
1. **晚补此前已经发生的历史事件**，记录实际发生时间，不把阶段按录入顺序倒退；
2. **结束后真实发生的新后续**，例如接受 Offer 后的报到沟通、条件变更或招聘方撤回。

这不等于默认重新开启招聘流程。误结束纠错见 DM-35；后来现实继续同一次尝试时，按 DM-39 明确记录真实变化。接受 Offer 不自动创建任职。

<a id="DM-07"></a>
### DM-07｜沟通与其来源

**状态：目标**

沟通属于一个机会，涵盖文字、电话及其他真实沟通；谈薪和后续报到联系是用途，不是第二套沟通系统。文字或转写可以明确更正，但不会仅因出现“面试”“Offer”就自动建立现实活动。

同一现实沟通从不同入口被引用时，应复用同一个来源身份或明确建立引用，不制造两份可独立修改的原文。被面试或研究引用的沟通不能因归档导致来源断裂；彻底清除遵守 DM-38。

<a id="DM-08"></a>
### DM-08｜公司研究与机会研究的内容所有者

**状态：目标**

CompanyResearch 保存可以跨同公司机会复用的公司层信息。OpportunityResearch 保存本次岗位、团队、招聘流程、招聘背景、机会当前判断和待确认问题。每个 owner 至多一份当前研究；界面可以合称“岗位情报”，但不改变 owner。

机会私有内容不会因公司相同自动共享。把一条机会内容提升为公司内容时，必须明确告诉用户共享范围会扩大：
- 用户手工明确选择 CompanyResearch 并保存，直接生效，不再走 AI 审批；
- AI 提议提升时，按 AI-10 审批。

提升后，公司级通用陈述由 CompanyResearch 成为唯一可修改正本；原 OpportunityResearch 可以保留“来源于这次机会”的引用或机会特有补充，但不能继续维护一份相同可编辑正文。

<a id="DM-09"></a>
### DM-09｜机会研究与机会 Wiki 的唯一正本

**状态：目标**

岗位职责、团队、招聘流程、招聘背景及“这次机会当前怎样判断”等重叠内容，由 **OpportunityResearch** 维护唯一可修改正本。机会 Wiki 可以在阅读时引用或展示这些研究条目，但不再保存一份可独立修改的同义正文。

机会 Wiki 仍可保存不属于 OpportunityResearch 的机会范围语义，例如用户对自己在这次机会中的决策理由、行动复盘或其他明确不属于岗位情报的知识。若一条内容同时符合两类，先选择唯一 owner，再由另一入口引用，不能双写。

<a id="DM-10"></a>
### DM-10｜研究条目的证据语义

**状态：目标**

ResearchItem 有稳定身份，可更正、补证、撤回。陈述性质（事实陈述、推断、未知）、来源是否只有线索、是否存在支持摘录、用户是否确认、是否独立核验、当前是否有效，是**可以并存的不同维度**，不组成自动升级流水线。

用户接受 AI 建议只表示采纳，不等于独立核验；标题和链接只表示线索。用户手工更正正文会形成新的当前陈述：旧陈述的“用户确认”“独立核验”只属于旧版本，不能自动继承到改写后的新内容；仍适用的来源和证据需重新判断。撤回的条目不再作为当前有效内容，必要历史仍可识别。

<a id="DM-11"></a>
### DM-11｜原始材料及范围

**状态：目标**

原始材料回答原文与出处是什么，可能来自粘贴文字、文档、沟通、面试转写、项目资料或收到的原件；它本身不保证内容真实。材料归明确对象或个人范围；姓名提及不自动建立人物。已有来源直接按原身份引用，不为统一入口再复制正文。

同一现实原件从多个业务入口使用时，尽量引用同一个来源身份；不能因为“从另一个页面导入”就生成一份可独立更正的重复原件。AI 复盘、研究结论、Wiki 和简历表达不是原件。

<a id="DM-12"></a>
### DM-12｜材料生命周期按业务含义区分

**状态：目标**

材料生命周期依据它在现实中的含义，不依据“手工输入还是导入”简单分类：

- **证据型原件**：用户保存来证明当时内容的材料，正常情况下不做随意原地改写；知识变化不反写原件。
- **可更正记录**：例如用户维护的沟通文字记录、Interview Transcript，可明确修正当前文本；不要求长期保留被替换的旧全文。
- **冻结历史材料**：收到的 Offer 原件、实际发送的简历/PDF/Greeting 等，不能用普通编辑覆盖。
- **当前内容**：简历当前稿自动保存；准备、终版复盘各维护当前内容；Wiki 另有修订史。

误导入、归错对象或包含敏感内容时，不要求用户为了保留“原始性”永久留着错误/敏感值；可以走 DM-38 的明确纠正、重新归属或永久清除路径。不得用日志、提案正文或“审计”名义偷偷长期保留本应清除或不应版本化的旧全文。

<a id="DM-13"></a>
### DM-13｜来源引用、来源变化与当前认识

**状态：目标**

来源引用应定位具体材料及当时可识别的版本，并说明用途。旧版本不再可读时明确说明，不把最新版冒充旧来源。历史简历证明当时写了什么，不证明现在事实仍如此。

当支持当前研究、Wiki 或复盘的来源发生实质变化时，不自动改写用户正文，也不把全部相关内容一刀切失效；受影响的陈述应显式提示“依据已变化/待复核”，后续高风险使用前重新判断支持是否仍成立。更正“独立负责”为“参与”后，不能从旧投递稿把夸大表述重新灌回当前认识。

<a id="DM-14"></a>
### DM-14｜Wiki 的内容和归属

**状态：目标**

每条知识属于一个明确项目、任职、机会、已确认人物、个人或长期认知范围。内容类型统一为 **事实陈述、观察、待验证判断**；`Fact` 只是陈述性质，不自动表示“用户已确认”或“独立核实”。

手工知识可以没有来源，必须如实说明由用户记录；带来源的事实陈述应有相应材料支持。正式采纳不等于独立核验。一份材料可支持多条知识，一条知识可引用多份材料。知识不拥有业务对象的身份、状态或真实关系。机会私有知识不进入全局长期知识默认列表；DM-09 已归 OpportunityResearch 的内容只引用展示，不重复维护正文。

<a id="DM-15"></a>
### DM-15｜Wiki 修订、退役和长期认知

**状态：目标**

知识更新、退役、恢复保持同一身份并保留变化历史。默认读当前有效内容；退役只是退出当前列表，不是物理删除。长期认知属于 Wiki，可手工维护个人方法、规律和长期理解；不恢复自动跨经历提炼的新入口。历史提案保留与处理方式遵守 MG-03，不能为回看历史而重建退役引擎。

<a id="DM-16"></a>
### DM-16｜项目独立存在

**状态：目标**

项目保存名称、描述、自由标签、状态及状态说明，可选关联零或一段当前任职，不属于任职的子容器。状态为进行中、暂停、完成、取消。用户认为仍是同一项目时，改名或转方向保持项目身份，不建立分叉、替代或合并关系图。个人项目不强制创建任职或协作者。

项目曾真实完成/取消后的重新推进规则由 DM-36 唯一负责；误点状态仍按 DM-39 作为纠错处理。

<a id="DM-17"></a>
### DM-17｜任职与历史语境

**状态：目标**

Employment 表示一段真实任职环境，保存公司信息、岗位、时间、当前目标、任职内人物、资料和知识，并展示关联项目。多段任职或项目时间可以重叠。只有现实开始任职后才成立；接受 Offer 不自动创建任职。

Employment 的计划结束、实际结束与结束后修正规则由 DM-34 唯一负责；本条只维护 Employment 的身份与历史语境。

<a id="DM-18"></a>
### DM-18｜人物是任职内的明确身份

**状态：目标**

Person 属于某段 Employment，不是跨工作的全局通讯录。同名或重复出现不自动合并、建档或确认身份。用户手工创建人物本身就是身份确认，不再二次确认。人物本体保持轻量身份和任职角色；明确要求、承诺、观察及待验证判断进入该人物的 Wiki 范围，不生成人格、心理或信任评分。

误把材料或项目关系关联到同名的错误人物时，修正原关系，不通过合并人物掩盖错误；历史上曾经错误关联的痕迹按 DM-39 作为纠错记录处理。

<a id="DM-19"></a>
### DM-19｜任职角色与项目职责分开

**状态：目标**

一个项目可关联多个当前任职中的已确认人物，一个人物可参与多个项目。同一项目与人物在同一历史语境下只建立一份协作关系。人物在 Employment 中的职务，与在每个 Project 中的自由填写职责分开；修改一个不影响其他。

人物升职、退出项目、重新加入等现实变化，保留过去角色/参与记录并更新当前关系，不把过去改写成从未发生。

<a id="DM-20"></a>
### DM-20｜项目换任职时的关系历史

**状态：目标**

项目解绑旧 Employment、变为个人项目或关联新的 Employment 时，旧协作者和项目职责保留在原任职的历史语境；它们不继续算作新任职下的当前协作关系。

新的当前协作者由用户明确选择，不能按同名 Person 自动迁移。可以先完成项目当前任职关系的变更，但系统必须让旧关系明确转为历史而非静默隐藏或删除。

<a id="DM-21"></a>
### DM-21｜独立当前简历

**状态：目标**

需要加工简历时才为机会建立当前稿。首次无可用版本时进入 A4 基础模板；已有版本可选择复制内容，之后完全独立。已有当前稿再次打开仍是原稿。身份区按 DM-01 使用最新资料。

用户在面试、Offer 等后续阶段才第一次需要简历，也可以创建当前稿；建立简历不会制造一条投递记录或让阶段倒退。不要求跨简历复制谱系，也不把复制动作等同于来源核实。

<a id="DM-22"></a>
### DM-22｜普通版本、导出物与恢复

**状态：目标**

自动保存仅保存当前稿，不制造版本。主动命名保存形成普通 ResumeVersion，属于创建它的 ResumeDocument，冻结当时内容及对应 PDF。恢复版本只更新当前稿，不修改源版本。

从其他机会的普通版本复制，只复制内容作为新当前稿来源；源版本身份仍属于原文稿，不转移 owner。导出 PDF 不要求先创建命名版本：每次 Career 导出的 PDF 应能识别其当时源简历/版本与内容快照，作为可选的“实际发送材料”候选，直到用户明确清除。删除普通版本不得破坏已经独立保留的投递历史。

<a id="DM-23"></a>
### DM-23｜一次真实首次投递与实际发送材料

**状态：目标**

“记录已投递”只登记用户确认已经发生的首次正式发送，不替用户发送。每机会至多一次首次 Submission。登记时分开表达：

1. 现实发送确实发生；
2. 本次是否使用简历；
3. 当时发送的简历内容是否已知；
4. 实际文件是否仍可获得。

若实际发送的 PDF/内容可获得，应保存独立的 Submission 历史材料，不拿后来当前稿或重新生成文件冒充。该发送材料归本次 Submission；即使内容来自别的机会的普通版本，也不转移源版本 owner，也不自动创建本机会的当前稿。

如果用户是在事后补录，明确知道发送过简历但原文件已不可得，仍可诚实登记“使用了简历、原文件缺失/内容部分未知”；不能逼用户改选“不用简历”。这与“系统本来承诺保存文件但保存失败”不同：后者仍应作为本次保存失败，不得借“文件缺失”伪装成功。

重复同一次登记取回同一结果，不生成第二次 Submission。业务时间遵守 DM-40；后期补录和后续发送见 DM-25。

<a id="DM-24"></a>
### DM-24｜没有、空白、未知和文件缺失不是一回事

**状态：目标**

明确本次未用简历、使用了简历但内容未知、内容已知但原文件缺失、完整材料仍在，是不同事实。未使用 Greeting、确实发送了空 Greeting、历史未记录 Greeting，以及已保存具体内容也分别表达。当前已有简历但本次没用，不能事后补成已发送。

<a id="DM-25"></a>
### DM-25｜后期建稿、补录首次投递与再次发送材料

**状态：目标**

三个动作分开：

- **后期首次建稿**：只要机会仍需要材料，任何阶段都可首次建立当前简历；不倒退阶段。
- **补录首次真实投递**：可以补记此前实际发生的首次 Submission，填写/选择当时真实业务日期和实际材料状态；不按录入时间重写阶段历史。
- **首次投递后的再次发送**：不建立第二个 Submission，作为一条真实沟通/材料发送活动记录，并冻结这次实际发送的材料或诚实记录文件缺失。

补录、补发都不能改写第一次 Submission 的原快照。业务时间及晚录规则见 DM-39、DM-40。

<a id="DM-26"></a>
### DM-26｜真实轮次与模拟

**状态：目标**

真实 InterviewSession 属于机会；一个真实轮次可有零到多次模拟。每次 Simulation 必须绑定同机会的一轮真实面试，不能绑定模拟或跨机会。现实新一轮才新建真实轮次；同一轮排期、改期和待重约不改身份。创建轮次不等于完成面试，模拟也不改变真实轮次或机会阶段。

<a id="DM-27"></a>
### DM-27｜确认轮次时允许日期未知

**状态：目标**

只要现实已经确认“存在这一轮面试”，即使日期尚未确定也可以创建轮次并显示“待排期”。稍后补日期、改期、临时取消待重约都保持同一轮身份。不能自动填今天、午夜或虚构排期。

历史补录一轮已经完成但具体日期未知时，同样允许记录日期未知；完成状态与日期完整度是两件事。

<a id="DM-28"></a>
### DM-28｜轮次状态与纠错

**状态：目标**

真实轮次至少能表达：待排期、已排期、已完成、永久取消；临时取消等待重约与永久取消分开。Simulation 只表达自身待完成、完成或取消，不冒充真实排期。排期与待重约属于同一轮；完成或取消一轮不自行改变 Opportunity 当前结果。

误完成/误永久取消的纠错规则由 DM-37 唯一负责；现实新一轮仍按 DM-26 才新建 InterviewSession。

<a id="DM-29"></a>
### DM-29｜准备、文字稿与终版复盘

**状态：目标**

每个真实轮次至多一份当前准备；每场真实或模拟面试至多一份当前文字稿和一份当前 Final Review。准备内容可以部分为空。复盘关注本轮结论、关键问答、跨问题模式、新信息发现、下一轮建议，用户可手工编辑。

文字稿可明确更正；不长期并存同等地位的 AI 原版复盘和用户终版。更正文字稿不自动改写现有复盘，但其来源支持发生变化时按 DM-13 提示待复核。复盘保存不自动形成职业事实。AI 生成准备或复盘时遵守 AI-10 的“草稿采用”规则。

<a id="DM-30"></a>
### DM-30｜模拟中的真实本人补充可受控回流

**状态：目标**

模拟面试官和角色扮演内容永远不能成为现实公司、岗位或 Offer 事实。用户本人在模拟中发现自己真实做过、但职业资料漏记的内容时，可以**主动选择具体片段，并明确确认它表达现实经历**，然后生成待审 Wiki Proposal。

首版允许目标为个人/长期认知 Wiki，或明确关联 Project 的 Wiki；仍按 Wiki 逐条审批。它不直接修改 Profile、Resume、OpportunityResearch 或 CompanyResearch；需要这些修改时进入对应正式任务。系统不自动扫描整场模拟寻找“可回流事实”。

<a id="DM-31"></a>
### DM-31｜Offer 条件、有效性、谈薪与接受依据

**状态：目标**

一个机会至多一份当前 Offer。用户确认现实收到后记录；Offer 维护当前条件及其是否仍可被视为当前有效条件，收到的原始材料不可普通覆盖。岗位、地点、薪酬不能仅从 JD 自动当作 Offer 条件。

谈薪沟通与正式条件更新分开。用户点击接受时，必须留下**当时接受的条件快照/明确引用**。若当时存在书面或其他原始材料，应一并保留；若现实中从未存在原件，或历史补录时原件已经丢失，则如实记录“无原件/原件缺失”、已知条件、未知项和来源说明，不能拿当前条件或新生成文件冒充当时依据。系统本次原本承诺保存原件却保存失败，仍属于本次保存失败，不能伪装成历史材料缺失。

Opportunity 当前结果统一拥有接受/进行中/招聘方终止/用户退出的当前结论，Offer 不维护第二套相反结果。**只有当当前仍生效的条件就是用户已经接受的条件时，当前结果才保持 accepted。** 如果招聘方明确用新的有效条件替代了已接受条件，而用户尚未接受新条件，则 phase 仍为 Offer、当前结果回到 active，旧 accepted 及其接受依据作为历史保留；用户接受新条件后形成新的接受依据并再次进入 accepted。若招聘方撤回机会且没有继续可决定的有效条件，则按招聘方终止处理；用户主动退出则按 withdrawn 处理。

不要求每次谈薪都形成完整条件版本链，但每次真正接受所依据的条件必须稳定可回看；后续变化遵守 DM-39，不能改写过去曾经接受过什么。

<a id="DM-32"></a>
### DM-32｜薪酬信息不混成一个数字

**状态：建议**

建议保留保证现金、浮动收入、权益、一次性收入、支付周期和未知条件的区别。不能把未确认、估算与保证收入混成“确定总包”。本条不要求照搬任何计算器，也不把历史未提供自动合计解释成永久禁止计算。

<a id="DM-33"></a>
### DM-33｜活动与进度只是展示

**状态：目标**

Opportunity 活动流从创建、投递、沟通、真实/模拟面试、Offer、谈薪、结束、后续真实联系和明确纠错等实际记录产生，点击回到对应对象。Simulation 明确标记为模拟，不冒充招聘方面试。普通保存、字号调整、AI 重跑、接受建议不刷成求职活动。

阶段日期来自实际阶段进入事件；晚录旧历史不按录入顺序改写阶段日期，新增后续轮次不重置首次进入面试的日期。活动摘要、筛选、AI 进度和待办数量不是第二份业务事实。

<a id="DM-34"></a>
### DM-34｜任职结束与结束后的修正

**状态：目标**

计划结束日期只是计划，不使当前任职提前变为历史。用户确认现实已经结束时记录实际结束日期并进入历史语境；结束后相关人物、角色、承诺、项目关联和材料继续可读。

历史内容写错时按同一对象明确更正并保留变化；后来真实变化与纠错分开。任职结束不会自动结束独立 Project。

<a id="DM-35"></a>
### DM-35｜误结束机会的纠错

**状态：目标**

误点用户退出、招聘方终止或接受 Offer 时，允许在同一个 Opportunity 上明确纠错并保留原变化及修正说明，不制造第二次尝试，也不改写冻结材料。真实重新申请仍创建新 Opportunity。

如果不是误操作，而是后来现实真的重新继续、用户改变决定或招聘方改变结果，按 DM-39 记录新的现实变化，不把后来变化伪装成“之前从未发生”。

<a id="DM-36"></a>
### DM-36｜完成或取消项目后重新推进

**状态：目标**

用户仍认为是同一个 Project 且现实重新维护时，可以明确从完成/取消重新进入进行中，并保留过去状态与说明。若之前只是误点完成/取消，则走 DM-39 的纠错路径。只有用户认为已经是另一件独立项目时才新建 Project。

<a id="DM-37"></a>
### DM-37｜面试终态误操作纠错

**状态：目标**

误把某轮标为已完成或永久取消时，修正同一 InterviewSession，保留纠错说明；不创建假的第二轮，也不自动重置 Opportunity 的首次面试阶段日期。真实后来发生的新一轮仍按 DM-26 新建。

<a id="DM-38"></a>
### DM-38｜归档、纠正归属与永久清除

**状态：目标**

为了减少列表负担使用归档/退出当前视图，不冒充永久删除。误导入、归错对象或包含敏感信息时，用户可以发起明确的纠正归属或永久清除；完整业务对象也可以发起永久清除，但必须先展示它关联的材料、知识、附件、冻结历史和其他引用，以及本地备份可能仍含副本的事实。

共享材料或被多处引用的来源不得静默级联删除：用户需要明确知道哪些引用会失去原文、哪些独立对象继续保留。永久清除后，系统不得继续把被清除的正文当作可读来源；可以保留不含敏感正文的必要“已清除”状态以解释断链。外部 Provider、用户已下载/发送的文件或其他机器副本不能承诺同步撤回。

普通永久删除与敏感清除可以共用影响预览，但不能以“归档”假装已彻底删除。

<a id="DM-39"></a>
### DM-39｜晚录、纠错与后来真实变化必须分开

**状态：目标**

- **晚录**：事情过去已经真实发生，只是今天才录入。保存实际业务时间（已知则记录，未知则明确未知）和独立录入时间；不按录入顺序制造阶段倒退。
- **纠错**：原记录本来就写错或点错。修正同一现实对象/事件，并保留足以解释此次修正的历史；不制造第二个现实事件。
- **后来真实变化**：原记录当时正确，后来现实发生了变化。新增/更新当前状态并保留旧历史，不把旧事实改写成“从未发生”。

只有现实中确实出现新的独立对象或事件时，才新建新 Opportunity、InterviewSession 等业务对象。

<a id="DM-40"></a>
### DM-40｜业务日期、时刻、时区与录入时间

**状态：目标**

业务时间首先表达现实语义：确认日、预约日/时刻、完成日、投递日、接受日、实际结束日、录入时间互不替代。只有日期时就保存日期；没有日期时明确未知；不能为了技术方便补午夜或今天。

需要精确时刻时同时保留对应时区/偏移，显示时可以按用户当前时区转换，但不得丢失原事件含义。补录使用实际发生日期而非录入日；若实际日期未知就保持未知。默认“今天”只用于用户当下明确登记“刚刚/今天发生”的事件，不用于历史补录猜测。
